# Commercial control: the contract for the six parallel slices

Six features are built in parallel, each end to end (domain, application, infrastructure, API, tests, Angular screens, docs), on one
shared foundation. This file is the contract: what already exists, who owns which files, the conventions every slice follows, and each
slice's rules. Where a rule below is a business default the owner has not yet confirmed, it is marked **Default** and goes into the
assumptions list of `docs/business-rules.md` (section 10) when the slices are integrated.

Read first: `AGENTS.md`, `CLAUDE.md`, `docs/development/vertical-slice-guide.md`, `docs/business-rules.md` (sections 1 to 6), and one
finished slice end to end for patterns: **Inventory** (`Cms.Domain/Features/Inventory`, `Cms.Application/Features/Inventory`,
`Cms.Infrastructure/Features/Inventory`, `Cms.Api/Endpoints/InventoryEndpoints.cs`, `web/src/app/features/inventory`) and **Payroll**.

## 3. Conventions every slice follows

**Money and quantities.** Money is `long` minor units (centavos) named `...Minor`. Quantities are `decimal`. Percentages and rates are
basis points (`int`, 10,000 = 100%) named `...Bps`. Never `double` or `float`. Round half away from zero, once, at the line, then add
rounded figures (see `LineAmounts` and `PayrollCalculator`: multiply first, divide last). Every amount a person types is bounded by
`MoneyLimits` (`Guard` helpers or `MoneyLimits.CheckAmount`); a sum of bounded lines cannot overflow. An index (CPI, SPI) is in basis
points. The contract price and billing amounts include VAT; use `LineAmounts.FromBase` with the company VAT rate **snapshotted** on the record.

**Records.** Aggregates derive from `AggregateRoot` (tenant, `Version` concurrency token). Private setters, a private parameterless
constructor for EF, a guarded factory that enforces invariants and returns all problems together (`ValidationErrors`). Child rows carry
`TenantId` and a foreign key (`Restrict`). String columns have `HasMaxLength`. Business dates are `DateOnly` judged in the company time
zone (`organization.TodayLocal(clock.UtcNow)`); instants are `DateTimeOffset` UTC. Financial records are **voided or reversed with a reason,
never deleted**; master data is archived. A void/reversal on an archived project is refused ("Restore it first"): call
`project.EnsureNotArchived()` on every affected project before changing a financial record. New records need
`project.EnsureCanReceiveRecordsFor(subProjectId)`.

**Services and endpoints.** Public `*Service` classes in Application are registered automatically. One use case per method; load,
`ConcurrencyGuard.Ensure(entity.Version, request.Version)`, call domain methods, `audit.Record(...)`, one `unitOfWork.SaveChangesAsync`.
Audit summaries never contain pay figures or free text a person typed that could (reasons stay on the record). Retriable creates take an
optional `ClientRequestId` (unique per company with a filtered index): a repeat returns the original, and a request id reused for something
else is refused (see `PayrollService`). Repositories and readers are `*Repository`/`*Reader` in Infrastructure (registered automatically):
the reader projects straight to DTOs in SQL, with a **fixed number of statements however many rows exist** and paging for lists. Endpoints
are Minimal APIs in an `IEndpointModule` with `RequirePermission(...)`; DTOs are flat records; failures are RFC 9457 problem details by
exception type (`ValidationFailedException` 422, `DomainRuleException` 409, `ConcurrencyConflictException` 409, `NotFoundException` 404).
Every endpoint names a permission; the endpoint-security test enforces it.

**UI language.** For the audience (Project Manager, Cost Engineer, Accountant, Warehouse Keeper, HR Officer): plain words with a next
action, buttons that name the result ("Approve purchase order", not "Submit"), money as "₱1,250,000.00", dates as "3 Dec 2026", errors that
say what happened and what to do. No codes or system terms.

**Guard what is not ready.** A feature that depends on something that may not be set up ships switched on behind one capability check
that falls back to the manual path, says so in plain words at the point of use, and never loses the person's work. It never turns on an
effect that spends or confirms money without a person: **recording a payment is a person saying "this was paid"; the system never pays or
collects.**

**Angular.** Standalone components, signals, `inject()`, `@if`/`@for`, strict types, no `any`. Feature folder with `*-api.ts` (the only HTTP),
`*-state.ts`, `*.models.ts`, `*.routes.ts`, colocated Vitest specs. The server owns calculations (totals, VAT, retention, earned value): the
client displays what the API sends and never duplicates a rule; a preview before saving calls the server or shows only what the
server returned. Reuse `shared/ui` (button, dialog, field, status chip, page header, empty state, pager, skeleton, alert,
api-error-alert, tab-nav, scroll-region) and the money/date helpers in `shared/presentation`. Router owns shareable filters; no gradients
(`npm run check:no-gradients`); plain backend writes go through the API (`npm run check:server-backed-interactions`).

**UI standards (`.agents/references/ui-ux-design-standards.md`).** Design at 375 x 812 first; hold at 768 x 1024 and 1440 x 900 with no
horizontal page scroll; 44 px targets; visible focus; 4.5:1 text contrast; one primary action per screen; show a thing when its moment
arrives (no empty tiles, zero chips, or tools for something that does not exist: an empty list says what it is for and offers the one
next step); one answer in one place (a figure shown in two places comes from one server calculation); an action a person may not use
is absent, not greyed out; an archived project is read-only with one line saying why. Dialogs keep their actions on screen at 375 x 667.
Report screens of scroll, words and buttons per page at 375 px for each new page.

**Tests (minimum per slice).** Domain unit tests for every rule (exact centavos, boundaries, every refusal message field), API tests on
the real SQL Server host for each endpoint family (happy path, every refusal, a wrong role gets 403 for each permission boundary, a second
company gets 404 for each id it did not create, a stale version is a 409, a repeated `ClientRequestId`), a fixed-statement-count test for
each list or report endpoint, and Vitest specs for state, presentation helpers and each page's key behaviour. Use
`SqlServerFact`, `CmsApiFactory`, `ApiClient`, `TenantSeeder`, `CostingTestKit` / `WorkforceTestKit` as the existing tests do. A test
asserts the exact outcome, never "does not throw". Run only your affected tests, once each: build once, then `dotnet test <project> --no-build
--filter ...` and `npm test --prefix web -- --watch=false --include <path>`; no wide or background test commands; the lead runs the full
suites. Set `CMS_TEST_SQLSERVER` (already exported). Fix what fails, re-run only that.

**Performance.** Triage every change in one line. These slices add read paths and lists: no per-row queries, no hydration of full
histories for a summary, paging for lists, grouped SQL for totals; assert the statement count of each list/report endpoint.

**Docs you write.** `docs/api/<feature>.md` (endpoints, requests, responses, errors, permissions: follow `docs/api/costing.md`) and
`docs/rules-drafts/<feature>.md` (the rules of your feature in the wording of `docs/business-rules.md`, numbered subsections, including a
**Decisions that rest on assumptions** list). The lead merges the rule drafts into `docs/business-rules.md` and deletes the drafts.

**Demo data.** Provide `Cms.Infrastructure/Seeding/<Feature>Demo.cs` with a `public static async Task SeedAsync(CmsDbContext db, ...)` that
adds a believable demo for the Riverside Residences project the seeder already creates (read `DevelopmentSeeder.cs`; the lead wires it in).
Use the existing demo users and workers where needed. Keep it small, deterministic and obviously fictional.

**Git.** Work in your own worktree on your own branch; commit in meaningful steps; do **not** push. Stage only your slice's files and
never any migration. The lead squash-merges your branch. Stop any server or database you start (drop your throwaway databases).

**Report** (final message): routes and endpoints added; contract points other slices or the lead must know; the rules you chose where the
spec left room; tests run and results; what you did not run and why; the `Performance:` line with statement counts; layout measurements
(screens of scroll, words, buttons at 375 px per page); anything you found wrong in shared code (describe, do not edit); remaining risk.

## 4. Where the slices meet

* **A and E** each add an `ICommitmentSource` (a `*CommitmentSource` class). Open remainder never counts what is already actual cost: A
  subtracts the cost entries linked to the order line, E subtracts the certified claims. Both report net and gross.
* **A and the costing UI.** Only A edits the cost-entry dialog and the dashboard/Budget-tab commitment display. E's `Subcontract` origin
  needs one union member and label in the Costs tab.
* **C and the Budget tab.** C changes how budget lines are created (`EnsureBudgetIsOpen` in `BudgetLineService`) and adds the chip and
  the locked message; it does not restructure the tab.
* **B and D.** The billing form's "suggested from progress" calls `GET /api/projects/{id}/progress` from the browser when the person
  holds `progress.read` and ignores a refusal; there is no backend coupling.
* **D and C.** Billing is limited by the project's contract price at the time, which change orders revise; D reads `Project.ContractPriceMinor`
  and nothing else of C's.
* **F and the rest of payroll.** F is the only slice that edits payroll. `PayrollRun.Approve` and the labor-cost posting are unchanged: the
  posted labor cost still equals gross pay; deductions (statutory and manual) reduce net pay only, and the employer's share is recorded,
  shown and exported but is **not** posted to a project (Default).

## 6. The slices

### B. Progress and earned value

**Outcome.** A project manager records how far along each budget line is and sees earned value: what the work done is worth against what
was spent and what was planned, and what the project is forecast to cost.

* `ProgressEntry` (append-only, never edited or deleted): project, budget line, `AsOfDate` (business date, not in the future), `PercentCompleteBps`
  (0 to 10,000), optional note (300), who and when, optional `ClientRequestId` for the batch. The line's **current** percent is the entry
  with the latest (`AsOfDate`, recorded time) not after the requested date. A lower percent than the current one needs a note (rework) or
  is refused with a field error. Only active budget lines of a project that can receive records.
* Recording is a batch (`POST /api/projects/{id}/progress`): an as-of date and up to 200 `{budgetLineId, percentBps, note?}`; all or nothing; a
  repeat with the same `ClientRequestId` returns the original; lines that did not change from their current percent are skipped (no
  entry), and it is an error to submit nothing that changed.
* Read (`GET /api/projects/{id}/progress?asOf=`): per active line its current percent, last update date, the line's budget on the comparison
  basis, its earned value; roll-ups by division and for the project; the earned-value block. `GET /api/budget-lines/{id}/progress`: a line's history (paged).
* **Earned value (all in minor units; per-line rounding once; indices in basis points).** On the company's comparison basis:
  `BAC` = sum of active budget lines. `EV` = sum over lines of `round(line budget x percent / 10,000)`. `AC` = posted actual cost (the same
  figure as the dashboard). `PV` = `round(BAC x plannedPercent)` where plannedPercent is the linear share of time from the project's start date
  to its target end date elapsed on the as-of date (0 before the start, 100% after the end); `null` when the project has no target end date.
  `CV = EV - AC`, `SV = EV - PV` (null without PV). `CPI = EV x 10,000 / AC` (null when `AC = 0`), `SPI = EV x 10,000 / PV` (null when `PV` is null or 0).
  `EAC = BAC` while `EV = 0` or `AC = 0`, otherwise `round(BAC x AC / EV)` (the cost index method); `ETC = max(0, EAC - AC)`; `VAC = BAC - EAC`;
  percent complete = `EV x 10,000 / BAC` (null when `BAC = 0`). **Forecast margin** = contract price (VAT included) minus `EAC` computed on gross
  amounts, null without a contract price: compute the gross figures separately when the basis is net. Put the formulas in one pure domain
  class with exact worked-example tests (including a project ahead of schedule and over budget, and each null case).
* No effect on the dashboard or the cost summary beyond what already exists.
* **UI.** The project **Progress** tab (`ProjectProgressTab`): before any progress exists, an empty state ("Record progress to see how far along
  the project is") and the update form; afterwards the summary leads (percent complete, earned value against spent, forecast to finish and
  the forecast margin when there is a price, plain-worded: "Spent ₱x for work worth ₱y"), then lines grouped by division (a division
  folds open), each with its percent, last update, and a number field with a quick stepper to change it; one **Save progress** with an
  as-of date (default today) and a count of lines changed. A line history opens in a dialog. People without `progress.write` see the figures only;
  an archived project is read-only. Explain CPI and SPI in plain words ("Each peso spent is earning 93 centavos of work").

### A. Purchasing (suppliers screens, purchase orders, committed cost)

**Outcome.** Cost engineers raise purchase orders to suppliers against a project, get them approved, and see the money committed but not
yet invoiced, so a project's forecast includes it. Invoices recorded later are matched to the order line.

* `PurchaseOrder` (aggregate): `Number` ("PO-0001", company sequence `purchase-order`, taken at creation), supplier (must be an active supplier-kind
  firm), project and optional sub-project (can receive records), order date (not in the future) and optional expected date (not before the order
  date), optional supplier reference (80) and notes (500), status **Draft, Approved, Closed, Cancelled**, lines (1 to 100), created/approved/closed
  by and when. A line: line number, description (200), optional classification (division/WBS/main scope as on cost lines), item type, quantity, unit, unit
  cost, VAT treatment and the **company VAT rate snapshot**; its net, VAT and gross come from the shared line rules (`CostLineRules`, `LineAmounts`). The order's total is the sum of its lines.
* Workflow: Draft (editable: replace the lines) -> **Approve** (`purchasing.approve`) -> lines locked. **Cancel** (reason) a draft or an approved order that
  has no invoice matched to it. **Close** (reason optional) an approved order: the unspent remainder is released (a supplier delivered less). A
  closed or cancelled order is final. Archived project: no new orders, and no approve/cancel/close ("restore it first").
* **Committed cost.** Per line: `remaining = max(0, line amount - matched invoices)` where matched invoices are the posted cost entries linked to the line
  (net and gross separately). Open commitment of a project = the sum of `remaining` over lines of **Approved** orders. A voided cost entry stops counting as matched, so
  the remainder returns. `PurchaseOrderCommitmentSource : ICommitmentSource` returns it per project in one grouped statement.
* **Matching an invoice.** `CostEntry.PurchaseOrderLineId` (optional, foreign key, set when the entry is created or edited): the line must belong to the same project
  and to an **Approved** order. An invoice larger than the line is allowed; the order page shows the line as "over by ₱x" and the commitment is zero for it.
  The order page lists the matched invoices (bounded) and, per line, ordered, invoiced and remaining.
* Endpoints (`/api/purchase-orders`): list (project, supplier, status, search; paged), get, create, update draft, approve, cancel, close; plus the order's
  matched invoices in the get. Suppliers already have an API: build the screens.
* **UI.** Section **Purchasing** (`/purchasing`): the orders list (status chips, a project filter, one primary "New purchase order"), the order page
  (summary, lines, matched invoices, the next step as one primary button: Approve for an approver, otherwise nothing), the draft form (supplier
  picker with the firm's kind, project and sub-project, lines added one at a time in a dialog, totals shown from the server's calculation), a **Suppliers**
  list and form (add, edit, archive, restore). The project **Purchases** tab (`ProjectPurchasesTab`) lists the project's orders with "New purchase order"
  for it. In the cost-entry dialog (`features/costing/project-costs-tab`) add an optional **Against a purchase order** choice, shown only when the project has approved
  order lines, listing "PO-0003 line 2, Rebar 16 mm, ₱x remaining"; choosing one prefills the supplier name and description. **Commitments display**:
  where the dashboard row and the project Budget tab show the cost position, when `commitments` is present show "Committed ₱x" and "Forecast ₱y" with the forecast health
  chip ("Forecast over budget" in a warning tone); absent when nothing is committed. Update `dashboard.models.ts` and `costing.models.ts`.

### C. Change orders and the budget baseline

**Outcome.** Once the budget is agreed it is frozen as the baseline; later changes to scope or price go through approved change orders, so the original,
the changes and the revised budget and contract price are always explainable.

* `Project` gains `BudgetBaselineLockedAtUtc`, `BaselineBudgetNetMinor`, `BaselineBudgetGrossMinor` and `BaselineContractPriceMinor` (null until locked).
  **Lock** (`changeorders.approve`; needs at least one active budget line; records the sums of active lines and the contract price; project must not be archived).
  **Unlock** (`changeorders.approve`, with a reason) only while no change order has been approved. While locked, creating, editing and removing budget lines in
  `BudgetLineService` is refused ("The budget is locked. Record a change order to change it."); change orders apply through the domain, not that service.
  `ProjectDto` carries `budgetBaselineLocked`.
* `ChangeOrder` (aggregate): `Number` ("CO-001", per project, taken at submission), title (120), description (1,000), reason (client request, design change, site
  condition, error or omission, other), `ContractPriceDeltaMinor` (signed, VAT included; the resulting price stays between 0 and the limit and needs an existing price),
  status **Draft, Submitted, Approved, Rejected, Voided**, lines (0 to 100; at least one line or a price change), who and when for each step, decision reason.
  A line is one of: **Add** (a new budget line: classification, description, item type, quantity, unit, unit cost, VAT treatment, date),
  **Revise** (an existing active budget line gets a new quantity and unit cost; its other fields keep), **Omit** (an existing active budget line is removed). Amounts use the shared line rules.
* Draft editable; **Submit** (`changeorders.manage`); **Approve** / **Reject** with reason (`changeorders.approve`). Approving applies, in one save: Add creates a budget line
  marked with its change order (`BudgetLine.ChangeOrderId`); Revise keeps the previous quantity and unit cost on the change order line and updates the line; Omit removes the
  line with the reason "Change order CO-001"; the contract price moves by the delta. The change order records its net and gross budget effect. Targets must still be active.
* **Void an approved change order** (`changeorders.approve`, reason): reverses every line (Add lines are removed, Revise restores the previous values, Omit reinstates the line
  via `BudgetLine.Reinstate`) and the price delta, and is refused while a **later approved** change order exists on the project ("Void CO-003 first") or the project is archived.
  A Draft or Submitted change order is voided (discarded) with a reason, never deleted.
* `GET /api/projects/{id}/budget-baseline`: locked or not, original budget (net, gross) and contract price, approved changes (budget net/gross, price), **revised** budget and
  price, the current sum of active lines (it equals original + approved changes: assert it), pending (submitted) exposure.
* **UI.** The project **Changes** tab (`ProjectChangesTab`): the baseline card (Original, Changes, Revised for the budget and for the contract price; one line of plain words)
  with **Lock the budget** for approvers while unlocked and a short explanation of what locking does; the list of change orders (status chip, number, title, effect); "New change order"
  (for managers); the change order page with its lines, effect and the actions allowed for the person (Submit; Approve and Reject; Void) and the audit trail line. Add/Revise/Omit
  lines are added one at a time in a dialog, with Revise/Omit choosing from the active budget lines. The Budget tab: a chip "Change order CO-001" on lines it created, and, when locked,
  the add/edit/remove controls replaced by one line: "The budget is locked. Record a change order to change it." with a link to the Changes tab.

### D. Client billing and retention

**Outcome.** The accounts side bills the client against the contract, holds retention, records what the client pays, and sees what is still to collect.

* `ProjectBillingTerms` (aggregate, one per project, created on first save): `RetentionBps` (0 to 3,000; **Default 10%** when no terms exist), `CreditableWithholdingBps` (0 to 1,000; **Default 0**:
  the client withholds this share of the amount before VAT at payment and gives a certificate), `PaymentTermsDays` (0 to 180; **Default 30**). `billing.manage` edits them.
* `ClientInvoice` (aggregate): kind **Progress** or **RetentionRelease**; project; `Number` ("BILL-0001", company sequence `client-invoice`, **taken at issue**; a draft shows "Draft"); billing date (not in the
  future); description (200); status **Draft, Issued, Void**. A **Progress** bill states `CumulativeWorkMinor`: the VAT-included value of all work billed to date including this bill. It must be greater than the
  previous issued bill's cumulative and not exceed the project's contract price (the project needs a price). Then: `ThisBillGrossMinor = cumulative - previous cumulative`; the net/VAT split uses
  `LineAmounts.FromBase` inclusive with the company VAT rate snapshotted; `RetentionMinor = round(gross x retentionBps / 10,000)` (the rate snapshotted from the terms); `WithholdingMinor = round(net x
  withholdingBps / 10,000)`; **`NetReceivableMinor = gross - retention - withholding`**. A **RetentionRelease** bill releases held retention: an amount up to `retention held - released`, only when the
  project is **Completed** (**Default**), no VAT (it was billed with the work), no further retention or withholding; receivable = the amount.
* **Issue** (`billing.approve`): re-checks the cumulative chain against the latest issued bill (a draft made earlier may now be stale: refuse with a reload message), assigns the number, locks the bill. **Void**
  an issued bill (`billing.approve`, reason): only the latest issued bill of the project, only while no payment is recorded against it; a Draft is discarded with a reason. Archived project: read-only.
* `ClientPayment`: against an issued bill; amount (greater than zero, not more than the bill's outstanding), paid-on date (not in the future), method (bank transfer, cheque, cash, other), reference (80), note;
  `billing.manage` records it; `billing.approve` voids it with a reason. **Recording a payment is a person saying it was received; nothing is collected automatically.**
* Derived (never stored as a status): paid, outstanding, due date = billing date + terms days (snapshotted on the bill), **overdue** when today is past due and something is outstanding.
* Reads: per project (`/api/projects/{id}/billing`): contract price, billed to date, percent billed, retention held and released, collected, outstanding, overdue amount, the bills (paged);
  company-wide (`/api/billing/receivables`): one row per project with an outstanding amount or retention held, totals, overdue first; bills list with filters (project, status, overdue).
* **UI.** Section **Billing** (`/billing`): the receivables overview (per project: outstanding, overdue badge, retention held; one primary action per row: Open); the project **Billing** tab
  (`ProjectBillingTab`): billing terms (folded until needed), the money line (contract price, billed to date, collected, still to collect, retention held), the bills with status chips,
  "New bill" for managers: the form asks for **work completed to date** (VAT included), shows the server's computed breakdown (this bill, retention, withholding, net receivable) before saving, and
  shows "Suggested from progress: X% of the contract" when the person can read progress (call `GET /api/projects/{id}/progress`, ignore failures); the bill page with its breakdown, Issue (approvers),
  Record payment, Void, and a RetentionRelease form when the project is completed and retention is held. Nothing resembling "send to client" or "collect": none exists.

### E. Subcontracts

**Outcome.** The company awards work to subcontractors, certifies their progress claims (which become project cost), holds retention, and records what it has paid.

* `Subcontract` (aggregate): `Number` ("SC-0001", company sequence `subcontract`, taken at creation), subcontractor (active firm of kind Subcontractor), project and optional sub-project (can receive records), title/scope
  (200), notes (500), contract sum (a base amount) with a **VAT treatment** (inclusive, exclusive or exempt) and the company VAT rate **snapshot** (the amounts follow the cost-line rules), `RetentionBps` (0 to 3,000,
  **Default 10%**), `WithholdingBps` (0 to 1,000, **Default 0**: tax the company withholds from the subcontractor's payment, on the amount before VAT), status **Draft, Active, Completed, Cancelled**, variations.
  A **variation** (signed base-amount delta with a description, `subcontracts.manage` while Draft, `subcontracts.approve` once Active) revises the contract sum; the revised sum must stay at least the certified work to date.
* Workflow: Draft -> **Award** (`subcontracts.approve`) -> Active -> **Complete** (`subcontracts.approve`; nothing uncertified remains drafted) ; **Cancel** (reason) a Draft, or an Active one with nothing certified. Archived project: read-only.
* `SubcontractClaim` (progress claim / payment certificate): claim number (1, 2, 3 per subcontract), claim date (not in the future), period end, `CumulativeWorkMinor` (base amount of all work done to date including this claim; greater than the previous certified cumulative; not
  more than the revised contract sum), status **Draft, Certified, Voided**. `ThisClaimBaseMinor = cumulative - previous`; amounts by the contract's VAT treatment and rate: net, VAT, gross; `RetentionMinor = round(gross x retentionBps / 10,000)`;
  `WithholdingMinor = round(net x withholdingBps / 10,000)`; **`NetPayableMinor = gross - retention - withholding`**. `subcontracts.manage` drafts a claim; **Certify** (`subcontracts.approve`) re-checks the chain, locks it, and **posts the work as project cost in the same save**:
  `CostEntry.RecordSystem(origin: Subcontract, originReferenceId: claim id, sourceName: subcontractor name, itemType: Subcontract, quantity 1, unit "l.s", the claim's base as the unit cost with the contract's VAT treatment and rate)` to the project/sub-project, dated the claim date. The posted
  cost equals the claim's net/VAT/gross exactly; retention is part of the cost (it is still owed). **Void** a certified claim (`subcontracts.approve`, reason): voids that cost entry in the same save; only the latest certified claim, only with no payment recorded against it, project not archived.
* `SubcontractPayment`: against a certified claim (amount > 0, not more than its outstanding net payable) or a **retention release** (up to retention held minus released, only when the subcontract is Completed); paid-on date (not in the future), method, reference, note;
  `subcontracts.approve` records it and voids it (reason). **Recording is a person saying it was paid; the system never pays.**
* `SubcontractCommitmentSource : ICommitmentSource`: for **Active** subcontracts, `max(0, revised contract sum - certified work)` per project (net and gross), one grouped statement.
* Reads: list (project, subcontractor, status, search; paged) with revised sum, certified to date, percent certified, retention held, paid, outstanding; get with claims and payments (bounded).
* **UI.** Section **Subcontracts** (`/subcontracts`): the list (status chips, a project filter, "New subcontract"); the page (summary money line, claims with status, payments, the one next step); the draft form (subcontractor picker, project,
  scope, contract sum and VAT treatment, retention); "New claim" asks for **work done to date** and shows the server's breakdown before saving; Certify, Void, Record payment, Release retention, Award, Complete, Cancel as dialogs for the people who may. The project
  **Subcontracts** tab (`ProjectSubcontractsTab`) lists that project's subcontracts with "New subcontract". Add the `Subcontract` origin to the Costs tab union and chip label ("Subcontractor"); the cost is corrected by voiding the claim.

### F. Statutory payroll deductions

**Outcome.** Payroll computes the employee's SSS, PhilHealth, Pag-IBIG contributions and withholding tax from tables the company keeps current, records the employer's share, and shows what to remit. **Statutory rates and brackets change by law and are never hard-coded**: they are
effective-dated data an accountant enters from the official schedules. Until a table is entered the feature says it needs setup and the person enters deductions by hand, as today.

* `StatutorySchedule` (aggregate): agency (**Sss, PhilHealth, PagIbig, WithholdingTax**), name (120), `EffectiveFrom` (date; unique per agency), status (Active or Retired), method:
  **Brackets** (rows: from, to or open-ended, employee amount, employer amount, per month), **Percentage** (employee rate and employer rate in basis points of the monthly base, base floor and ceiling, optional monthly minimum and maximum of each share),
  **TaxBrackets** (rows: from, to or open, base tax, rate in basis points on the excess over `from`). `PeriodBasis`: **Monthly** (table is per month) or **PerRun** (table is per pay run). Rows must start at 0, ascend with no gaps or overlaps, with exactly one open-ended last row; rates at most 100%.
  `statutory.manage` creates, edits (a schedule already used by an approved payroll is not editable: add a new effective date), retires; `payroll.read` reads. A schedule applies to a run when it is the Active schedule of the agency with the latest `EffectiveFrom` on or before the run's period end.
* Company setting **runs per month** (`Organization`: integer 1 to 4, **Default 2**) is needed: add it with the company settings change that is the one allowed edit to `Organization` (and its DTO and admin settings form). **Tell the lead in the report that you touched it.**
* Worker flags (`workforce.manage` edits; visible only with `payroll.read`): member of SSS, member of PhilHealth, member of Pag-IBIG (**Default true**), withholding-tax exempt (**Default false**; minimum-wage earners are exempt).
* **Calculation** (one pure domain class, `StatutoryCalculator`, exact worked-example tests per method): for each worker line in a draft: for a Monthly table the **monthly base is the run's gross pay x runs per month** (**Default**, an estimate; say so in the UI and in the rules) and the
  month's amount is divided by runs per month (rounded once, remainder to the last run: **Default**: do not model the remainder, round half away from zero each run); for a PerRun table the base is the run's gross. Percentage: `base` clamped to floor/ceiling, share = `round(base x rate / 10,000)`, clamped
  to min/max. Brackets: the row containing the base. Tax: taxable base = base minus the employee's SSS, PhilHealth and Pag-IBIG contributions of the same basis; tax = base tax + rate x (taxable - from); never negative; zero for an exempt worker.
  Employee shares reduce net pay as `PayrollDeduction` rows tagged `Statutory` with agency and schedule; employer shares are stored on the line (`EmployerShareMinor` per agency), shown and exported, **not posted to project cost** (**Default**).
  Deductions (statutory and manual) together still cannot exceed gross pay: when statutory alone would, the run does not fail: cap each statutory amount so the total equals gross, in agency order, and flag the line ("Deductions were limited to the pay").
* Draft creation computes statutory deductions when schedules exist. The HR officer can **adjust** an automatic amount (`payroll.run`, with a reason; becomes "Adjusted") or **recalculate** a draft (resets adjustments). `SetDeductions` keeps replacing only the **manual** set; automatic
  rows are not touched by it. An approved or voided run is final. The posted labor cost is unchanged (gross pay).
* **Capability check** `GET /api/statutory/status` (`payroll.read`): per agency **Available** (a schedule is in force today), **Needs setup** (none), with a plain message and the fallback. The payroll new-run page and the run page show one quiet line per agency that needs setup ("SSS contributions were
  not calculated because no SSS table is set up. Enter them as deductions, or ask an accountant to set the table up."); never an error, never a block.
* Reads: `GET /api/payroll-runs/{id}/statutory` (`payroll.read`): per agency totals (employee, employer, to remit) and per worker; the payroll register CSV gains the employee and employer statutory columns.
* **UI.** `/payroll/statutory` (reached from the Payroll page, a quiet link; `payroll.read` views, `statutory.manage` edits): status per agency, the schedules list (effective date, method, status), a schedule form with a bracket/percentage editor that works at 375 px (one row per card), "Copy from the previous schedule", retire. The run page shows the
  statutory deductions with their source ("SSS, calculated"), an Adjust dialog and a Recalculate action for drafts, and a remittance summary per agency. The worker form and page show the four flags to people who can see pay. The company settings form gets runs per month.
* **Demo data** is flagged "Illustrative demo table: replace with the official schedule" in the schedule name. Do not state or imply that any seeded figure is the legal rate.
